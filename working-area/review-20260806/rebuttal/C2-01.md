## psycopg 3 트랜잭션 동작 확인 (판정의 핵심)
- **`autocommit` 설정**: 저장소 전체에서 `psycopg.connect(...)` 호출은 `raw_deal_sink.py:85-91`(`connect_from_env`) **한 곳뿐**(Grep `psycopg\.connect` 결과 1건, 프로덕션 코드 기준). `autocommit=True`를 넘기지 않으므로 psycopg 3 기본값(`False`, 트랜잭션 모드)로 열린다.
- **`with conn:` / `conn.transaction()` 사용 여부**: 프로덕션 코드(`collector/src/collector/db/*.py`) 전체에서 `with self.connection.cursor() as cursor:` 패턴만 쓴다(6개 소스 파일에서 6회 매치) — **`with self.connection:`(커넥션 자체를 컨텍스트 매니저로) 또는 `conn.transaction()`은 프로덕션 코드에 0건**(Grep 확인). 커서만 닫힐 뿐 트랜잭션 상태는 그대로 남는다.
- **커넥션 공유 구조**: `__main__.py:278-286`(`_connect_if_needed`)이 명시적으로 "게시판·중고·폴링 상태·별칭이 한 커넥션을 공유하므로 여기서 한 번만 연다"고 주석까지 달려 있다. `RawDealSink`·`UsedListingSink`·`UsedSearchSource`·`SitePollStateSink`·`AliasSource` 다섯 개 싱크/소스가 전부 같은 `psycopg.Connection` 인스턴스를 받는다(99-103행).
- **결론**: 실패한 문장이 커넥션을 aborted 상태로 남긴다. `executemany` 도중 CHECK 위반이 나면(테스트로 실증됨) `commit()`은 실행되지 않고 세션은 PostgreSQL의 "current transaction is aborted, commands ignored until end of transaction block" 상태가 된다. `rollback()`을 부르는 코드가 어디에도 없으므로, 이 상태는 같은 커넥션을 쓰는 다음 쓰기(그리고 사실은 다음 **읽기**도 — `alias_source.all_aliases()`·`search_source.all_searches()`가 각 사이클 안에서 try/except 없이 호출됨)까지 그대로 이어진다.

## 반박 시도 (그 밖에 찾아본 것)
- **`SINK_FAILURE_LIMIT` 실체**: `__main__.py:65`에 `SINK_FAILURE_LIMIT = 3`으로 실재. `main()` 루프 187-190행에서 `sink_failures >= SINK_FAILURE_LIMIT`이면 `giving_up` 이벤트 후 `return 1`. `test_repeated_sink_failure_stops_the_process_instead_of_spinning`(test_main.py:291-305)이 `exit_code == 1`과 `giving_up["consecutive_sink_failures"] == SINK_FAILURE_LIMIT`을 관통 검증한다 — 단, 이 테스트의 `BrokenSink`는 순수 파이썬 mock이라 커넥션 오염 자체는 재현하지 않는다(아래 "대응 테스트" 참조).
- **재기동 복구 여부(`restart: on-failure`)**: `docker-compose.yml:138`에 `restart: on-failure` 확인, `stop_grace_period: 30s`도 141행에 확인. exit 1 후 재시작되면 `_connect_if_needed`가 **새 커넥션**을 다시 열므로 오염은 사라진다 — "영구"라기보다 "재시작으로 회복"이 맞다. 다만 원 발견도 39행에서 이를 인정하며("`restart: on-failure`가 결국 재시작해 회복은 되지만") 심각도를 "재시작 전까지 board+market 양쪽 모든 쓰기가 마비"로 정확히 좁혀 두었다 — 과장이 아니다. 만약 원인이 파서 버그처럼 **매 사이클 재발**하는 값이면(과거 `ENDED` 사고류) crash-loop이 된다는 지적도 타당하다(재수집마다 같은 배드 레코드가 다시 들어오므로).
- **실패의 흔적(로그·observability)**: `sink_error`(158-159행), `poll_state_error`(247-248행), `giving_up`(188-189행) 전부 구조화 JSON 이벤트로 남는다 — 침묵하지는 않는다. 다만 **직접 코드를 더 추적한 결과, 원 발견이 언급하지 않은 더 급한 실패 경로가 하나 있다**: `_poll_market`(202-232행)의 `for search in search_source.all_searches():`(209행)와 `main()`의 `alias_source.all_aliases()`(136행)는 **try/except로 감싸여 있지 않다.** 커넥션이 aborted 상태인 채로 다음 사이클(또는 같은 사이클의 시장 폴링 단계)에 이 호출이 실행되면, `psycopg.errors.InFailedSqlTransaction`이 **어디에도 잡히지 않고 `main()` 밖으로 전파**되어 `giving_up` 이벤트도 없이 프로세스가 트레이스백과 함께 죽는다. 결과적 종료코드(1)와 `restart: on-failure`의 재기동 자체는 같지만, "3회 연속 실패 후 우아하게 내려온다"는 설계 의도(코드 주석 17-18행)가 실제로는 **더 이르게, 더 거칠게 깨질 수 있다** — 이는 원 발견의 주장을 약화시키지 않고 오히려 보강한다.
- **대응 테스트**: `test_main.py`의 `BrokenSink`(255-266행)는 `raise RuntimeError`만 던지는 순수 mock으로, 실제 psycopg 커넥션·트랜잭션 상태를 전혀 다루지 않는다 — "예외 후 재시도/정지" 카운터 로직만 검증하고 "예외 후 같은 커넥션의 다른 쓰기(또는 읽기)가 실패하는가"는 다루지 않는다는 원 발견의 지적이 코드 확인 결과 정확하다. `test_raw_deal_sink.py`·`test_used_listing_sink.py`·`test_site_poll_state_sink.py`·`test_end_to_end_ingest.py`는 전부 `conftest.py:44-54`의 함수 스코프 `connection` 픽스처(테스트마다 새 커넥션 + 스키마 재생성)를 쓴다 — "CHECK 위반 이후 같은 커넥션을 여러 싱크가 재사용"하는 시나리오는 검색된 범위 내에서 어떤 테스트에도 없다.
- **도달 가능성(어떤 쓰기가 실제로 실패할 수 있는가)**: (1) CHECK 위반 — `raw_deal_post.status` 허용집합 밖 값(과거 `ENDED` 사고와 동일 계열, 파서 회귀 시 재발 가능), 테스트로 실증됨. (2) `used_listing_observation`은 insert-only이고 `ON CONFLICT` 절이 없다(`used_listing_sink.py:21-26`) — 유니크 제약이 있다면 중복 삽입 시 `UniqueViolation`도 같은 경로를 탈 수 있다(스키마 전수 대조는 안 했으나 원 발견의 핵심 주장에는 영향 없음). (3) DB 연결 끊김·네트워크 순단 등 일시 장애도 트랜잭션 도중이면 동일하게 aborted 상태를 남길 수 있다. 셋 다 "이론적 가정"이 아니라 최소 하나(CHECK 위반)는 테스트로 실증됐고, 과거 실제 사고(`ENDED`) 전례가 있다.

## 판정 근거
원 발견의 핵심 기술 주장 — ① psycopg 3 커넥션이 `autocommit=True` 없이(기본 트랜잭션 모드로) 열린다, ② 어떤 싱크도 `rollback()`을 호출하지 않는다, ③ 다섯 개 싱크/소스가 **하나의 커넥션을 공유**한다, ④ 이 조합으로 한 번의 쓰기 실패(CHECK 위반 등 실증된 트리거)가 같은 커넥션을 쓰는 후속 쓰기(및 실은 읽기까지)를 연쇄적으로 실패시킨다 — 를 전부 코드 원문에서 직접 재확인했고 어긋남이 없다. `SINK_FAILURE_LIMIT=3`·`giving_up`→`exit(1)`→`restart: on-failure` 메커니즘도 실재하며 "영구"보다는 "재시작 전까지 마비 + 파서 버그면 crash-loop 가능"이라는 원 발견의 정교한 표현이 정확하다. 오히려 `search_source.all_searches()`/`alias_source.all_aliases()`가 try/except 없이 호출된다는, 원 발견이 짚지 않은 지점까지 확인해 심각도가 과장이 아니라 오히려 더 심할 수 있음을 확인했다. 기존 테스트(`BrokenSink` mock, 함수 스코프 신규 커넥션 픽스처)가 정확히 이 경계를 비켜간다는 지적도 사실이다. 억지로 기각할 근거를 찾지 못했다 — CONFIRMED, High 등급 유지가 타당하다.
