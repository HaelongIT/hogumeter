## 레이스 실현·가시성 (핵심 반박 축)
- **부모가 `key`로 재마운트시키는가**: 아니다. `DecisionPage.tsx:341-347`에서
  ```tsx
  {variantId !== null && (
    <PurchasePanel
      variantId={variantId}
      demandAxisValue={demandAxisValue}
      prefill={variantId === initialVariantId ? purchasePrefill : null}
    />
  )}
  ```
  `key` prop이 없다. `variantId`가 11→12로 바뀌어도 React는 같은 `PurchasePanel` 컴포넌트 인스턴스를 재사용하고 effect만 재실행한다 — 재마운트가 아니라 조건부 렌더 트리 안에서 prop만 바뀐다(`variantId !== null`이 계속 true인 한 마운트 상태 유지). `App.tsx:68`의 `<DecisionPage initialVariantId={openVariantId} .../>`에도 `key`가 없어 상위에서도 강제 재마운트가 없다. state가 초기화될 여지가 없으므로 "재마운트로 무해해진다"는 방어는 성립하지 않는다.
- **전환 UI 조작과 속도**: `DecisionPage.tsx:152-163`의 네이티브 `<select>` `onChange`로 `setVariantId`를 직접 호출한다. 로딩 중 `disabled` 처리가 없어 요청이 진행 중이어도 셀렉트를 계속 조작할 수 있다. 네이티브 셀렉트는 값 변경마다 즉시 `onChange`가 발화하므로 사용자가 옵션을 연속으로 두 번 고르면(마우스 클릭 두 번, 또는 방향키+엔터 연타) 두 `listPurchases` 요청이 어렵지 않게 겹친다.
- **화면에서 구분 가능한가(variant 이름 표시)**: 아니다. 구매 목록(`PurchasePanel.tsx:143-166`)의 각 `<li>`는 구매가·구매일·상태칩·성적표/관찰문맥만 그리고, variant 이름이나 ID를 전혀 표시하지 않는다. "이 variant의 구매 기록이 없습니다"라는 문구도 `purchases.length === 0`일 때만 뜨고 목록이 채워지면 사라진다. 사용자가 셀렉트에서 방금 고른 variant 이름을 기억하고 있지 않는 한, 화면만 보고 "이건 다른 variant 기록"이라고 알아챌 단서가 없다.
- **로딩 상태가 가리는가**: 부분적이지만 레이스 자체는 못 막는다. effect 시작 시 `setPurchases(null)`이라 응답 대기 중엔 목록도 "없음" 문구도 안 뜨는 짧은 공백은 있다. 그러나 문제는 그 공백이 아니라 **응답의 도착 순서**다 — 새 요청(B)이 먼저 도착해 화면을 채운 뒤, 늦게 도착한 옛 요청(A)의 `.then(setPurchases)`가 그 위를 덮어쓰면 최종 상태가 A로 굳는다. 로딩 표시가 그 이후의 잘못된 덮어쓰기를 가리지 못한다.

## 반박 시도 (그 밖에 찾아본 것)
- **`PurchasePanel.test.tsx` 케이스**: `124-130`행 `'variant가 바뀌면 그 variant의 기록을 다시 부른다'` 테스트를 직접 읽었다.
  ```tsx
  const { rerender } = render(<PurchasePanel variantId={11} />)
  await waitFor(() => expect(api.listPurchases).toHaveBeenCalledWith(11))
  rerender(<PurchasePanel variantId={12} />)
  await waitFor(() => expect(api.listPurchases).toHaveBeenCalledWith(12))
  ```
  각 단계가 `waitFor`로 먼저 resolve된 뒤에야 다음 rerender가 일어나는 순차 시나리오다. `vi.spyOn(api, 'listPurchases').mockResolvedValue([])`도 즉시 resolve되는 단일 mock이라 응답 지연·순서 뒤바뀸을 표현할 수 없다. out-of-order 응답을 재현하는 테스트는 없음 — 가드도 없고 회귀를 잡는 테스트도 없다.
- **`DecisionPage.test.tsx`**: `<select>`에 로딩 중 `disabled` 처리가 있는지, 연속 전환을 막는 디바운스가 있는지 원문에서 확인 — 둘 다 없다(`DecisionPage.tsx:152-163`에 `disabled` 속성 자체가 없음).
- **`App.tsx`가 tab 전환 시 상태를 리셋하는지**: `openDecision`이 `purchasePrefill`은 리셋하지만(`App.tsx` 주석부 확인), `PurchasePanel` 자체의 재마운트와는 무관 — 프리필 초기화는 별개 값(`purchasePrefill`)이고 `purchases`/`error` state의 레이스와는 관계없다.

## 판정 근거
1. 인용된 코드(`PurchasePanel.tsx:74-78`, `reload` 정의부)가 원문과 정확히 일치하며, cleanup 자체가 없어 취소 메커니즘이 전무하다.
2. "다른 5개 파일은 같은 가드를 쓴다"는 주장을 5개 파일 전부에서 직접 확인했고 사실이다 — `PurchasePanel.tsx`만 예외적으로 누락됐다.
3. 부모(`DecisionPage`, `App`) 어디에도 `key` prop을 통한 강제 재마운트가 없어, variant 전환은 순수하게 state 갱신 + effect 재실행으로 처리된다. state가 초기화되지 않으므로 "재마운트가 무해하게 만든다"는 방어는 코드상 근거가 없다.
4. 전환은 로딩 중에도 막히지 않는 네이티브 `<select>` `onChange` 한 번으로 발생해, 사용자가 두 번 연속 고르면 요청이 쉽게 겹친다 — 실현 가능성이 낮다고 볼 근거가 없다.
5. 목록 항목에 variant 식별 정보가 전혀 없어, 레이스가 실현되면 사용자는 "다른 variant의 구매 기록"을 자기 variant의 기록으로 오인한다 — "이미 샀는가/얼마에 샀는가"를 오판하게 하는 이 시스템의 핵심 절대 원칙(정직성·판단은 사람)과 정면으로 부딪힌다.
6. `PurchasePanel.test.tsx`의 유일한 관련 테스트는 순차 시나리오만 검증해 이 결함을 못 잡는다.
5개 항목 모두 원 발견의 주장·심각도(High)를 그대로 뒷받침한다. 반박 근거를 찾지 못했다.
