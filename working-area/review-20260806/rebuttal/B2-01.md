# 반박 검증 — B2-01
## 판정: DOWNGRADED(High→Medium)

## 인용 재확인
| 원 발견이 인용한 위치 | 실제 코드와 일치 | 비고 |
|---|---|---|
| `HttpTelegramApi.java:89-92`(당시 `getUpdates`) — `response.statusCode()` 미검사, 바로 `response.body()` 파싱 | 일치 | 재확인 결과 라인 90-91(현재 파일 기준)이 정확히 이 코드. `HttpResponse<String> response = client.send(...); return parseCallbacks(response.body());` — 상태코드 변수조차 만들지 않는다. |
| `parseCallbacks`(:127 부근) — `result` 키가 없으면 조용히 빈 목록 반환 | 일치 | 현재 파일 127행 `if (!(root instanceof Map<?, ?> map) \|\| !(map.get("result") instanceof List<?> updates)) { return out; }`. 텔레그램 4xx 응답은 `{"ok":false,"error_code":...,"description":...}` 형태라 `result` 키가 없으므로 이 분기를 그대로 탄다 — 예외 없이 빈 리스트. |
| `answerCallbackQuery`·`editMessageText`가 `post()`의 상태코드를 버린다 | 일치 | 현재 파일 108행·116행에서 `post(...)`의 반환값(`int`)을 변수에 담지 않고 버린다. 더 나아가 **인터페이스 계약 자체가 `void`다**(`TelegramInboundApi.java:24,30`) — 구현이 상태를 돌려주고 싶어도 시그니처가 막는다. |
| `TelegramInboundPoller.poll()`은 `RuntimeException`만 잡아 HTTP 에러를 못 잡는다 | 부분 수정 필요 | `poll()`(:52-68)은 실제로 `catch (RuntimeException failure)`로 감싸긴 한다. 다만 위 두 항목 때문에 **애초에 예외가 발생하지 않는다** — 401/403 응답이 정상적으로 파싱되어 "빈 목록"이 되므로 catch 블록 자체가 이 시나리오에서 죽은 코드다. 원 발견의 결론("이 경로는 예외로도 걸리지 않는다")은 맞다. |

## 아웃바운드 vs 인바운드 처리 대조
| 메서드 | HTTP 상태 검사 | 본문 `ok` 검사 | 예외 전파 | 상위 처리 |
|---|---|---|---|---|
| `sendMessage`(아웃바운드, `post()` 경유) | O — `int` 반환 | 안 함(상태코드만) | 네트워크 단절만 `TelegramTransportException` | `TelegramAlertSender.classify()`가 OK/TRANSIENT/REJECTED로 분류, REJECTED는 `log.error`(SEC-08), 매 알림 발송마다 반복 |
| `TelegramAdminNotifier.notify()`(아웃바운드) | O(내부적으로 `sendMessage` 재사용) | 안 함 | transport 예외만 잡아 `log.warn` | 상태코드 미검사이므로 401/403 REJECTED도 `notify()` 관점에선 "성공"으로 간주(호출자에겐 성공/실패 신호 없음) — **관리 알림 채널 자신도 같은 결함을 안고 있다** |
| `getUpdates`(인바운드) | **X** | **X**(`result` 부재만 확인, `ok` 필드 자체는 안 봄) | 없음(정상 파싱되어 빈 목록 반환) | `poll()`의 for 루프가 0회 순회 — 아무 로그도 안 남음 |
| `answerCallbackQuery`(인바운드) | **X**(반환값 폐기) | 해당 없음(void) | 없음 | 없음 |
| `editMessageText`(인바운드) | **X**(반환값 폐기) | 해당 없음(void) | 없음 | 없음 |

## 반박 시도 (내가 실제로 찾아본 것)
- **본문 파싱이 실패를 드러내는가**: 안 드러난다. `parseCallbacks`는 `ok:false`를 명시적으로 검사하지 않고 `result` 키의 부재만으로 판단한다 — 우연히도 "빈 성공 응답"과 "실패 응답"이 같은 코드경로(빈 리스트 반환)로 수렴한다. 원 발견의 핵심 관찰은 정확하다.
- **상위 호출자(`TelegramInboundPoller`) 처리**: `poll()`은 for 루프가 빈 컬렉션이면 그냥 조용히 끝난다. `catch (RuntimeException)`는 있지만 이 실패 모드에서는 예외 자체가 발생하지 않아 트리거되지 않는다. `PipelineHealthMonitor`(연속 실패 카운트→`AdminNotifier`)에 대한 배선을 grep으로 확인했으나 `TelegramInboundPoller`는 그 컴포넌트를 전혀 참조하지 않는다 — `PipelineScheduler`만 `healthMonitor::onTick`을 쓴다. 인바운드 폴러는 파이프라인 헬스 체계 밖에 완전히 고립돼 있다.
- **"영구 정지"인가 "반복 실패"인가**: 둘 다 아니고 그보다 나쁘다 — 예외 자체가 안 나서 "실패로 인식되지도 않는" 상태다. 매 3초 정상 폴처럼 반복되며(`fixedDelay`), "업데이트 없음"(정상)과 "인증 거절"(비정상)이 코드상 구분 불가능하다. 다만 원 발견이 "영원히 멈춘다"고 단정한 트리거 시나리오(토큰 무효화)는 **아웃바운드도 함께 죽인다** — 같은 URL(`baseUrl = ".../bot" + botToken`)을 쓰므로 `sendMessage`도 401을 받는다. 이 경우 `TelegramAlertSender.post()`가 상태코드를 검사해 `classify()==REJECTED`로 `log.error`를 매 알림마다 남긴다. 즉 "완전한 침묵"은 인바운드 경로 **단독으로는** 사실이지만, 가장 그럴듯한 트리거(토큰 무효화)에서는 시스템 전체가 침묵하는 게 아니라 아웃바운드 쪽에서 로그 흔적이 남는다. 반대로 **아웃바운드는 멀쩡한데 인바운드만 죽는** 진짜 시나리오는 텔레그램 Bot API의 잘 알려진 제약(동시에 두 프로세스가 같은 토큰으로 `getUpdates`를 호출하면 한쪽이 409 Conflict를 받는다)에서 재배포 시 신·구 컨테이너가 잠시 겹치는 구간(이 프로젝트의 `docker compose up -d` 재배포 모델과 부합)에 실제로 일어날 수 있다 — 다만 이 경우는 이전 컨테이너가 완전히 내려가면 자연 해소되는 **일시적** 충돌이라 "영원히"는 과장이다.
- **실패의 흔적(로그·AdminNotifier·리포트·헬스)**: 인바운드 경로 자체에는 전혀 없음(확인됨: `PipelineHealthMonitor` 미배선, `AdminNotifier` 미호출, `TelegramInboundPoller`에 실패 카운터 없음, 헬스 엔드포인트(`HealthController`/`AlertStatusController`)도 인바운드 폴러 상태를 안 다룸 — `AlertStatusController`는 `AlertSender.delivers()`만 보고하며 이건 스텁/실전송 구분이지 인바운드 생존 여부가 아니다). `scripts/preflight.sh`도 텔레그램 관련 점검이 있지만(grep으로 존재만 확인, 배포 전 설정값 점검 성격 — 런타임 폴링 헬스는 아님).
- **대응 테스트**: 없음. `HttpTelegramApiTest` 부재 재확인(디렉터리 전체 리스트에 없음). `TelegramInboundPollerTest`는 `FakeInbound`(자체 인터페이스 구현)로 `HttpTelegramApi`의 상태코드 무시·`parseCallbacks` 로직을 완전히 우회한다 — 이 결함을 잡을 수 있는 테스트가 정말 하나도 없다.
- **도달 가능성**: 두 갈래로 나뉜다. ① 토큰 완전 무효화·봇 차단(사용자 행동 필요, 드묾) — 발생 시 아웃바운드도 같이 죽어 `log.error`로 흔적이 남고, 이 프로젝트는 "핫딜 알림이 옴"이 사용자가 상시 기대하는 신호라 알림이 끊기면 비교적 빨리 알아챌 개연성이 있다. ② 재배포 중 컨테이너 중복 기동(409 Conflict) — 아웃바운드는 멀쩡한 채 인바운드만 조용히 죽는 진짜 시나리오지만, 통상 짧게 자연 해소된다.

## 판정 근거
코드 사실관계(HTTP 상태 미검사·본문 파싱이 실패를 숨김·인바운드 폴러가 헬스 체계에서 완전히 고립·테스트 전무)는 전부 재확인했고 전적으로 CONFIRMED다 — 이 부분에서 원 발견을 반박할 지점을 찾지 못했다. 다만 심각도(High)에는 두 가지 근거로 동의하지 못한다.
1. **파급 범위**: 이 결함은 `PipelineScheduler`가 도는 핵심 파이프라인(수집→적재→기준가→알림 발송)에 전혀 영향을 주지 않는다. `TelegramInboundPoller`는 별도 `@Scheduled` 컴포넌트로, 죽어도 신품 알림·기준가 계산은 정상 작동한다. 과제가 제시한 High 기준("알림 오발화·미발화 / 파이프라인이 조용히 멈춤")에 해당하지 않는다 — 영향받는 건 미상 큐의 승격/기각/무시라는 부차 상호작용 기능이다.
2. **완충 경로 존재**: `ReviewQueueController`(`/api/v1/review-queue/{id}/promote`, `/reject`)가 텔레그램을 거치지 않는 REST 대안을 이미 제공한다. "채널 전체가 영구히 멈춘다"는 표현은 사실상 "가장 편한 채널(버튼)이 죽는다"이지 "손쓸 방법이 없다"가 아니다(단, 🔕무시는 REST 대응이 안 보여 이 경로는 진짜로 텔레그램 단독 의존).
3. **가장 그럴듯한 트리거(토큰 무효화)에서 완전한 침묵은 아니다** — 아웃바운드가 같이 죽으며 `log.error`(SEC-08) 흔적이 남고, 알림이 끊기는 것 자체가 1인용 사용자에게 조기 신호가 될 개연성이 있다.

원 발견의 기술적 진단·권고안(상태코드 검사 추가, 연속 실패 카운트→AdminNotifier)은 타당하고 실제 결함이 맞다 — 다만 실 서비스 영향은 "핵심 파이프라인 침묵"보다 "부차 기능의 조용한 저하 + 불완전한 완충 경로"에 가까워 Medium이 적절하다고 판단한다.

## 판정이 바뀔 조건
- `ReviewQueueController`의 REST 경로가 실제로는 CORS/인증/네트워크 노출 문제 등으로 실사용 불가능하다는 게 밝혀지면(예: web 미배선, 외부에서 못 침) → 완충 경로가 사라져 CONFIRMED(High) 쪽으로 재고려.
- 🔕무시(ignore) 액션이 하필 사후학습(Q-22) 등 다른 신품 파이프라인 정직성 로직에 실제로 연쇄 영향을 준다는 게 확인되면(예: 무시 학습이 안 돼 노이즈 필터링 품질이 전체 알림 신뢰도를 떨어뜨림) → High 재고려.
- 실측(토큰 발급 후 스파이크)에서 텔레그램이 401/403이 아니라 다른 형태(예: 항상 200 + `ok:false`, 혹은 커넥션 자체를 끊음)로 응답한다고 밝혀지면 이 반박의 "아웃바운드도 같이 죽어 흔적이 남는다"는 전제가 흔들릴 수 있음 — 재확인 필요.
