## 상태 초기화 경로 추적
| state 변수 | 언제 초기화되는가 | GROUPED→SPLIT(축 미선택) 전환 시 초기화되는가 |
|---|---|---|
| `demandAxisValue` | `variantId` 바뀔 때마다 effect1이 `setDemandAxisValue(null)` (83행 선언) | GROUPED variant에서는 축 선택 UI 자체가 없어 `demandAxisValue`가 처음부터 계속 `null`이었다 — effect1이 `null→null`을 쓰므로 **값 자체가 바뀌지 않는다**(React 배치 유무와 무관하게 이 렌더에서 `demandAxisValue`는 여전히 `null`) |
| `loaded` | 오직 조회 effect(119-142행) 본문 124행 `setLoaded(null)`에서만 초기화 | **초기화 안 됨** — 121행 조기 `return`이 124행 도달 전에 함수를 끝낸다. `demandAxis`(옵션 배열에서 온 안정된 참조, GROUPED면 `null`/SPLIT이면 축 객체)가 `variantId`와 함께 바뀌므로 이 조회 effect는 새 `variantId`로 다시 실행되지만, `demandAxisValue`가 여전히 `null`이고 새 `demandAxis`가 non-null이라 121행 조건이 참이 되어 즉시 반환한다 |

| `badge` | state 아님, `loaded && signalBadge(loaded.signal)`로 매 렌더 파생 | `loaded`가 안 지워지므로 `badge`도 옛 variant 것을 계속 가리킴 |

**원 발견의 "state bail-out" 설명에 대한 보정**: 원 발견은 "동일 값 갱신을 React가 bail-out해서" 문제가 생긴다고 서술하지만, 실제로는 그 메커니즘의 이름이 정확하지 않아도 결론은 같다 — `demandAxisValue`가 GROUPED 구간 내내 이미 `null`이었으므로 effect1이 실행되든 안 되든, bail-out이 있든 없든 **"이 렌더에서 demandAxisValue는 null이다"라는 사실 자체가 안 바뀐다.** 게다가 `variantId`·`demandAxis`가 둘 다 이번 커밋에서 바뀌었으므로 조회 effect는 (bail-out 여부와 무관하게) 어차피 새 `variantId`로 재실행된다. 즉 인용된 메커니즘의 정밀한 설명은 다소 과잉이지만, **관찰된 결함 자체(조기 반환이 `loaded`를 안 지운다)는 코드를 그대로 따라가면 재현된다.** 판정에는 영향 없음.

## 렌더 시점 방어 (핵심 반박 축)
- **조건부 렌더링이 가리는가**: 가리지 않는다. `loaded`가 안 지워지므로 234행 `{loaded && badge && (<section aria-label="판단 요약" ...>` 조건이 그대로 참이 되어 옛 variant의 `loaded.signal`·`loaded.benchmark`·`loaded.cadence`·`loaded.coupang`을 담은 판단 요약 섹션이 계속 렌더된다. 226행의 스켈레톤(`{variantId !== null && !loaded && !error && (...)}`)도 `loaded !== null`이라 뜨지 않는다 — 로딩 중이라는 신호조차 없다.
- **로딩 상태가 가리는가**: 가리지 않는다. 위와 동일 — `loaded`가 비지 않으므로 스켈레톤이 아니라 "완료된 답"처럼 보이는 히어로 섹션이 그대로 유지된다.
- **제품/variant 이름이 함께 바뀌어 사용자가 알아채는가**: `<select>`의 선택값(154행 `value={variantId ?? ''}`)은 `variantId` state가 실제로 바뀌었으므로 새 variant(예: 갤럭시 25 — 256GB)로 정확히 바뀐다. 그러나 234-336행 "판단 요약" 섹션 안에는 **제품/variant 이름을 표시하는 요소가 전혀 없다**(신호등 램프, 헤드라인, 기준가·갭·주기·쿠팡관측가 라인, 최근 딜의 사이트/날짜만 나열) — 옛 제품 이름이 남지도, 새 제품 이름이 뜨지도 않는다. 즉 셀렉트만 보면 갤럭시로 바뀐 게 맞는데, 그 아래 신호등·기준가·갭 숫자는 여전히 아이폰 것이라 **사용자가 셀렉트와 요약을 함께 보지 않는 한(혹은 208-213행의 "색상을 고르세요" 안내 문구를 놓치면) 값이 stale이라는 걸 알아챌 단서가 요약 섹션 자체엔 없다.** 208-213행 수요축 안내(`role="note" aria-label="수요축 안내"`)는 요약 섹션과 별개 블록으로 함께 뜨긴 하지만, 안내문과 판단요약 히어로 중 어느 쪽에 시선이 먼저 가는지는 이 프로젝트의 CSS 위계(히어로가 "이 화면의 답") 상 히어로 쪽이다.

## 반박 시도 (그 밖에 찾아본 것)
- **`DecisionPage.test.tsx`의 variant 전환 케이스**: `describe('DecisionPage — 수요축 분리 제품', …)`(259-302행)는 `beforeEach`에서 `listProducts`를 갤럭시(SPLIT) **하나만** 반환하도록 모킹한다(273행). GROUPED 제품(아이폰)과 SPLIT 제품(갤럭시)이 **같은 렌더 트리에 함께 존재하며 그 사이를 전환하는 테스트는 파일 전체에 없다** — `iphone` fixture를 쓰는 `describe`들은 전부 `listProducts`가 `[iphone]`만 반환한다(58행, 306행, 353행 등). `App.test.tsx`도 동일(단일 variant 등록 후 판단화면 진입 한 경로뿐, 68행). **가드 없음 — 원 발견의 주장과 일치.**
- **도달 가능성(UI 조작 경로)**: `selectable(products)`(53-61행)가 **등록된 모든 제품의 모든 variant를 평평하게 펴서 하나의 `<select>`에 나열**한다(GROUPED·SPLIT 구분 없이 한 목록). 즉 사용자가 GROUPED 제품 variant를 고르고 요약을 본 뒤, **같은 드롭다운에서 SPLIT 제품 variant를 바로 선택하는 조작이 정상 UI 경로로 가능하다** — 별도 내비게이션이나 우회 없이 셀렉트 두 번이면 재현된다. 실사용에서 신품(주로 GROUPED 단일 옵션) variant를 보다가 색상/용량이 갈리는(SPLIT) variant로 갈아타는 것은 드문 조작이 아니다.

## 판정 근거
1. 코드 원문을 라인 단위로 재확인한 결과, 인용된 두 `useEffect`와 조기 `return` 경로, 그 경로가 `setLoaded(null)`을 건너뛴다는 서술은 전부 사실과 일치한다.
2. "React state bail-out" 표현은 정밀하지 않지만(값이 애초에 안 바뀌므로 bail-out 유무와 결론이 무관), **핵심 주장 — GROUPED variant에서 이미 `demandAxisValue=null`인 상태로 SPLIT variant(축 미선택)로 전환하면 조회 effect가 조기 반환하며 `loaded`를 지우지 않는다 — 는 코드를 그대로 따라가면 재현된다.**
3. 렌더 시점 방어가 전혀 없다: `loaded`가 비지 않으므로 로딩 스켈레톤도 안 뜨고, "판단 요약" 섹션이 그대로 유지되며, 그 섹션 안에는 제품/variant 이름이 없어 사용자가 셀렉트를 다시 확인하지 않는 한 stale 여부를 판별할 단서가 부족하다.
4. 이 화면(`DecisionPage`)은 프로젝트 정의상 "이 값을 보고 구매를 결정하는" 메인 판단 화면이고, 절대 원칙("정직성" — 값이 없으면 없다고 보여야 한다)에 정면으로 위배된다 — 다른 제품의 신호등·기준가·갭이 "현재 선택된 제품의 답"인 것처럼 남는다.
5. 도달 가능성이 높다(같은 드롭다운에서 셀렉트 두 번), 지속 시간도 "사용자가 축 값을 고를 때까지 — 영구히 가능"이라 원 발견의 실패 시나리오와 심각도(High) 판정이 그대로 유지된다.
6. 기존 테스트(`DecisionPage.test.tsx`, `App.test.tsx`) 어디에도 GROUPED↔SPLIT 혼재 전환 시나리오가 없어 이 경로를 막는 장치가 전혀 없다는 원 발견의 "이미 막는 장치 확인" 결론도 그대로 맞다.

## 판정이 바뀔 조건
- 만약 `selectable()`이 GROUPED/SPLIT을 별도 드롭다운·별도 화면으로 분리해 같은 셀렉트에서 직접 전환이 불가능하다면 도달 가능성이 낮아져 심각도가 내려갈 수 있다 — 그러나 실제로는 하나의 평평한 목록이라 해당 없음.
- 만약 "판단 요약" 섹션 안에 제품/variant 이름이 함께 렌더되어 stale 값이 즉시 눈에 띈다면 심각도를 Medium으로 낮출 여지가 있다 — 그러나 실제로는 그런 표시가 없음(위 렌더 확인).
- 만약 조회 effect의 조기 return 앞에 `setLoaded(null)`을 호출하는 별도 effect나 가드가 존재한다면 REFUTED — 그러나 코드 전체(1-353행)를 확인한 결과 그런 가드는 없다.
